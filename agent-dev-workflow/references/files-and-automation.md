# 文件分类、产物清理与自动化

任务开工检查资源、新增脚本或文档、生成文件以及收尾判断产物去留时读取本文件。沿用项目现有目录、工程命令和授权范围。检查采用[最低必要检查规则](development-modes.md)，安装替换、备份及恢复按[交付与同步](delivery.md)执行。

## 开工前检查可复用资源

在方案定稿和派工前检查任务共用资源，各模块实施前补查模块特有资源：

1. 从根 README、计划/结构索引和工程命令定义定位现有工具、文档、样例及领域 skill，再搜索候选目录并读取相关内容；沿用已知入口，不反复扫描全库或只按文件名判断可用。
2. 对照当前源码/配置确认适用版本、输入输出、依赖、参数、执行目录与副作用。文档陈旧或与实现冲突时标记并核实；找到文件只证明它存在，不代表内容准确或工具已验证。盘点优先读定义与已有证据，不盲跑安装、删除、发布等有副作用的命令。
3. 简记已检查的资源入口、适用约束和缺口，为下节自动化判断提供依据；个人小任务沿用现有计划/日志，不新增资源台账。
4. 主 agent 将已检查的共用入口、可复用命令、已知缺口和使用约束交给 subagent，明确本模块仍需检查的资源；子 agent 在模块实施前完成定向补查，发现不适用或冲突时回报并调整，不重复全仓盘点。部分检查不能标为全部完成，随后按任务风险验证实际使用结果。

## 规划阶段的自动化判断

共用资源检查后、模块拆分与派工前，主 agent 对任务作一次自动化判断：

1. 识别本次重复步骤、批量处理、易错操作、需要可靠重跑的环节，以及有明确依据的后续复用需求。一次性批量任务也可能值得自动化，不必等待任务多次发生。
2. 先复用已确认适用的工具；部分满足时评估扩展；没有适用工具或扩展不合适时，只有节省操作、减少错误或可靠重跑的收益足以抵偿实现与维护成本，才新建最小可复用工具。收益不足或一条可靠命令已够用时直接处理，不为假想复用搭框架，也不为包装已有命令新增无用途的配置层或脚手架。已有工具不合适时说明实际缺口，避免为复用之名做成本更高的改造。
3. 在现有计划简记“复用 / 扩展 / 新建 / 直接处理”及理由，个人小任务一行即可。选用工具时写明或引用输入输出、使用者、唯一负责人、相关验证和依赖工作包；存放、参数及失败处理沿用下文脚本规则，不另建评估表或审批。
4. 把工具工作与其使用者的依赖纳入派工；依赖步骤在工具通过相关验证后使用，不依赖它的工作继续。无须先完成所有工具才启动其他实施。

实施中发现新的重复需求或既有工具不再适用时，按实际证据补充判断并调整计划、接口和依赖，不机械沿用最初选择。

## 映射布局并分开存放工具和文档

结合资源检查，在现有结构索引中登记类别对应的路径、生成命令和使用者。目录名不同但职责清楚就复用；工具代码与详细文档各有唯一维护入口，彼此链接。根目录保留 README、规则、计划/结构入口及工程所需配置；简短 `--help`、docstring 和工具包局部 README 可就近保留，需独立维护的详细工具说明放文档目录。小项目的用户使用说明可完整保留在根 README，后续拆分时留下链接，不复制多份正文。

| 类别 | 可选位置示例 | 存放边界 |
| --- | --- | --- |
| 源码与运行资源 | `src/`、`assets/`、模块目录 | 维护输入；普通构建输出不混回源码，项目约定的生成源码保留既有位置并标明生成命令 |
| 文档 | `docs/usage/`、`docs/development/`、`docs/changes/`、skill 的 `references/` | 按读者和用途分类，根入口链接唯一正文；详细工具说明链接可执行入口 |
| 长期自动化工具 | `scripts/`、`tools/`，按需分 `build/`、`test/`、`maintenance/` | 可复用、随源码维护的工具代码；使用入口链接对应详细说明 |
| 构建中间产物 | `build/<module>/`、`out/build/<task>/` | 编译、转换、打包暂存等可重建结果 |
| 最终版本产物 | `dist/<version-or-candidate>/`、`artifacts/releases/` | 可交付文件及其来源、清单；候选与已发布状态明确 |
| 测试报告与诊断证据 | `artifacts/tests/<task>/`、`artifacts/diagnostics/<issue>/` | 原始日志、截图、转储和报告；按任务/问题关联来源 |
| 任务临时试验 | `.work/<task>/`、`tmp/<task>/` | 一次性工具放 `scripts/`，记录/说明放 `records/` 或 `docs/`，生成结果放 `outputs/`；不作为长期入口 |
| 缓存 | 工具既有缓存目录、`.cache/<tool>/` | 可重建的加速数据，与制品和用户数据分开 |
| 回退材料（确有需要时） | 已有版本记录/发布包或既定备份位置 | 优先复用可恢复版本；需另备份的数据避免被通用构建清理覆盖 |

以上是职责映射，不是必建目录清单。小项目可把中间产物、报告和临时试验放在一个工作目录的不同子目录；最终交付制品仍与临时杂物分开。随数量增长再按用途、模块、任务或版本分组，避免把所有文件平铺到根目录或同一个 `output/`。已有混放先核对调用、链接和使用者，在本次范围内渐进归位并更新引用；不为套用示例批量搬迁、建立空目录或开展无关重构。

## 生成前确定输出与来源

- 执行构建、转换、测试或批量生成前，确定输入、输出目录、覆盖范围和归属；优先使用工程命令已有的输出参数。工具固定写入某目录时明确登记，不能假设换工作区就已隔离它。
- 并行任务使用各自的任务/候选目录，不共享默认输出、临时文件名或测试数据。无法隔离的输出由指定负责人串行生成、校验和清理；subagent 只处理自己拥有的产物。
- 制品目录按候选来源管理，沿用 [交付规则](delivery.md) 记录必要的源码版本、生成入口和产物位置，不默认生成哈希或逐文件比对。源码含未提交内容时如实记录，不能把旧输出或混入其他候选的文件当成本次构建。普通临时文件不逐个建立发布级清单。
- 按 [交付规则](delivery.md) 确定运行资源和明确需要的文档清单并据此组装发布包；调试转储、试验输入、缓存、开发记录和私人配置不随目录整包混入。项目要求分发的许可证等文件仍纳入清单。
- 按项目约定维护忽略规则，避免提交生成垃圾。被忽略、未跟踪或位于产物目录都不构成删除授权，也不证明文件能够重建。

## 在明确节点清理

收尾前，主 agent 沿本次任务涉及的命令、实际输出目录、生成清单和子任务回报，找出项目产生的文件。包括工具自动生成、被 Git 忽略或未跟踪的输出，也包括这些位置中已被替代的旧版本和往次任务留下的已知产物。按用途归组判断**任务结束后还有谁需要这组文件、用来做什么**。有约定的支持、审计或回退期限时遵循约定，没有专门保留策略时直接按用途判断。

- **保留。** 有明确的交付、运行、后续开发、复现、支持或回退用途，按实际用途保留所需文件。正式报告、生成源码和长期回归样例都可能是项目生成的成果。
- **清理。** 已确认由项目管理、最后一个使用步骤已结束、且再无保留用途的输出，由负责人在授权范围内当场删除。共享输出由其既定负责人处理。归属和用途已经明确的项目旧包也按此处理。
- **暂留。** 归属不明、可能含用户修改或尚待下游确认时，留下相关项并记明可重新判断的条件，例如另一项任务读完数据或旧版支持期结束。其余已判明的文件照常处理。

| 时点 | 如何取舍 |
| --- | --- |
| 新安装包验收并交付 | 按[交付规则](delivery.md#产物保留与及时清理)判断替代关系。保留当前交付、支持或回退所需的包，删除已被替代且无保留用途的本地旧包、候选副本和打包暂存。 |
| 测试结束或修复验收通过 | 留下正式验收结果、已采用的回归样例和未结故障仍需的原始证据。清除用完的测试数据副本、临时环境、重复日志和截图。 |
| 开发阶段完成、成果移交或试验放弃 | 确认后续步骤已取得需要的输入，清除用完的中间文件、临时导出和一次性试验脚本。增量构建仍在复用的缓存保留，确需回收时优先用该工具的清理命令。 |

优先使用范围相符的工程清理命令，或直接处理已确认的具体路径。删除前确认真实路径位于获准处理的输出范围，清单生成后对象有变化时重新判断该项。混放目录只处理已确认的项，整目录递归清理须确认其内容均属可清范围，并避免沿符号链接或 junction 越界。Windows 使用同一 shell 的原生路径参数。保留用户数据和他人工作，文件名、年龄或一次搜索无结果均不足以判废弃。源码、长期脚本及文档的退役按普通代码变更核对引用、构建配置和使用入口，删除时更新引用并运行受影响检查。安装目录内的文件替换另按[交付规则](delivery.md)执行。

以实际执行结果确认清理完成，遇到占用、权限或命令失败时记录剩余路径及处理条件。重复出现的废弃输出，优先将清理接入最后使用它的现有测试、打包或交付命令。普通任务在收尾时直接处理即可。

## 主动编写并使用有价值的脚本

- 按 [规划阶段的自动化判断](#规划阶段的自动化判断) 实施所选工具方案，并在本任务实际使用；发现新证据时更新选择，避免只写脚本却继续重复手工操作。
- 预期持续复用的脚本进入已有 `scripts/`、`tools/` 或等价位置，按用途适度分组并随源码维护；一次性探查脚本放任务的 `scripts/`，结束时按上述条件清理。试验升级为长期入口时补齐参数、依赖和验证说明，工具与详细文档分别归位并互相链接。
- 参数化输入、输出及必要选项，提供简短帮助、清楚的成功/失败退出码和可定位的错误信息；明确覆盖与重跑行为。使用项目相对路径、配置或环境变量，不写死个人绝对路径，不把秘密写入源码、参数日志或产物。
- 批量删除、覆盖或部署先提供 `preview`/`dry-run`，或等价的具体操作清单；执行前重核目标和状态。预览不等于执行完成，也不替代既有授权。已有可靠工程入口能满足需要时，不另造通用删除脚本。
- 新增或修改脚本时，按 [最低必要检查规则](development-modes.md) 实际验证相关行为，失败路径仅在本次变更或具体操作风险需要时覆盖。未变脚本复用已有有效结果和本次正常调用结果，不每次重跑整套自测；仅需语法检查时不扩展为运行测试，目标涉及真实操作时也不把语法通过冒充操作完成。无法执行的环节写明未验证。
- 外部命令失败时保留原因并停止依赖步骤，核对真实状态后才有限重试。避免最后一步成功掩盖前面的失败，避免重复执行已成功的删除、发布或安装。

## 只记录维护所需信息

在现有结构索引、开发指南或交付记录补少量对应关系：**类别 → 实际目录 → 工具/文档入口或生成命令 → 保留或清理条件 → 负责人**。目录、命令或资源适用范围变化时同步更新，根入口仍可找到正文；不为本规范强制新增一套文件。

主 agent 在既有任务或交付记录汇总实际清理的类别、重要保留项及暂留条件。个人小任务一行即可，同类文件合并记录。没有产生或替代项目文件时省略该项。文档分工和事实记录按[文档规范](documentation.md)维护。
