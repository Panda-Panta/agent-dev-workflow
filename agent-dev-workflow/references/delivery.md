# 交付与双端同步

## 项目目标与授权

首次接管核对并补齐项目现有交付配置和此前明确约定；缺少记录时按需采用 [交付配置模板](../assets/delivery.template.md)，不为模板名称重复建文档。真实路径可放被忽略的本机配置，仓库只存环境变量名/模板，避免把用户名、令牌和本机秘密发布出去。

必须区分源码 checkout、构建产物目录与用户实际运行的软件目录。已有的已授权远端和软件目录沿用执行，分支采用下文默认与专项安排，不重复索取例行许可。远端不存在、分支语义不明或软件目录未提供时，先检查文档/配置；仍不明确才只问缺失项，其余工作继续。

仅发现某个 remote 或同名目录不等于确认它是交付目标。项目明确无本机安装形态时，把对应制品/部署目标写清；没有设置与“不适用”是不同状态。创建仓库、改变可见性、合并受保护分支、正式发布、强推和破坏性迁移按实际用户授权处理。

有 Git 的开发默认使用 `main` 和 `test`：`test` 承担开发、修复、集成与验证，`main` 保留通过验证的稳定结果。普通任务及每个 subagent 不自动创建额外分支。确有特殊需要时可以按实际用途命名专项分支，例如 `experiment/...`、`maintenance/...`；在现有计划简记理由、负责人、基线、合入目标和结束条件，无需新增固定审批。成果通常先集成 `test` 再验证晋升 `main`，用户明确指定其他目标时按具体要求执行。已有分支不自动删除、改名或覆盖；专项分支收尾先核对合入状态、保留价值及未推送工作，再按实际归属处理，不因任务完成删除他人分支。

按 [开发模式](development-modes.md) 标明软件目录的个人试用、共享测试或稳定正式用途。共同模式仍明确实际审查、合并和发布负责人；`test` 已同步不触发正式软件目录自动安装，候选只进入项目明确允许的独立试用/测试环境。

缺失目标按 [协作规则](human-first.md) 尽早明确；确需新操作许可时，先完成已授权的候选产物、差异清单和验证，再说明具体对象、影响及缺少的许可。上游协作规则不增加每次推送、安装都重新审批的步骤，也不替代平台本身的授权要求。

## 可追溯的候选版本

1. 检查工作区与暂存区，列出本次文件及用户原有修改，核对所依赖的版本。只暂存本次明确路径。已有暂存内容不能因为普通 `git commit` 被一并带入；采用明确路径提交或独立索引/checkout，并在提交后核验用户原有暂存状态。同文件混有用户改动时逐块隔离，不用整文件提交冒充安全隔离。
2. 更新计划、结构、开发日志、受影响的使用说明/版本变更和项目领域 skill，按 [文档规范](documentation.md) 检查相关操作与发布状态；完成所需验证，记录日志。无关旧失败单列；与交付相关的失败解决前不安装。
3. 形成候选源码提交，构建时基于该候选树生成制品。若用户修改仍留在工作区，使用隔离的候选 checkout 或证明构建输入与候选树一致。记录源码 commit、版本、构建命令、产物相对路径/大小/SHA-256；不能给包含未提交变化的产物标记为干净 commit 构建。
4. `test` 按既定检查和授权同步，需要 CI 构建时可先推送再取得该提交的产物与结果；不把本机最终制品当作所有 push 的前置条件。软件安装/发布前必须完成实际交付产物的必要离线/启动检查。优先复用项目既有构建和发布工具，不能把旧 dist 的存在当作新版本已构建。

按 [文件管理与自动化](files-and-automation.md) 区分构建中间目录、最终产物、验证报告与回退副本；每次构建使用独立候选目录，或仅在已确认的专用输出目录按清单清除上次中间文件。新版本验证成功前保留当前可用交付与必要回退。打包按明确清单纳入运行资源；发行包默认不附说明文件、非运行示例和包内校验文档，开发日志与使用知识仍在工程维护，用户明确要求的文档按清单交付。此默认针对软件包的附带说明；当交付物本身是文档或 skill 时，其正文、引用和模板就是交付内容，必要许可证与运行资源也不得遗漏。不递归打包整个项目；检查包内清单，排除本地配置、密钥、缓存、试验脚本和原始日志等非交付内容。

## 远程同步

先从配置核对用户自有仓库、实际远端和 `main`/`test`，不能把任意 remote 当成已授权目标。外部 PR 的仓库和源分支保持只读，固定其 head 后将需要的贡献集成到自有 `test`，保留作者归属，修复和验证也在 `test` 完成；不因外部 PR 例行另建集成分支或要求集成 PR。不得向外部源分支推送、改写历史或删除分支，`maintainer_can_modify=true` 不构成写入授权。

1. 在 `test` 整合本次变更和已知的 `main` 更新，固定已验收候选提交、审查结果、测试与构建输入。候选不能包含他人未验收的工作；共享 `test` 中有其他任务时先协调批次或等待其验收，不直接将整个最新分支晋升，也不删除或回退他人的工作来凑出候选。
2. `test` 验证完成后，沿用项目可用的既定偏好，选择 **PR `test` → `main`** 或 **将已验证结果直接合入 `main` 并普通推送**。个人模式可使用直接合入，不强制额外 PR 或每次询问；共同模式由已协调的负责人执行。平台分支保护要求 PR、审查或 CI 时满足其要求，不修改保护设置或用管理员绕过。
3. 晋升前核对远端 `main` 和候选是否仍与验证基线相符。`main` 有进展、候选增加内容或出现冲突时，先在 `test` 整合、修复并重验受影响部分，再晋升新的已验证候选；不在 `main` 临时修复后跳过验证。PR 也须核对最终 head，不能夹带创建 PR 后新增的未验收内容。
4. 只提交本次明确路径，普通推送；远端并发更新造成失败时查询实际状态，回到 `test` 安全整合并验证，不强推或覆盖无关工作。记录候选提交、实际 `main` 提交及所用 PR（如有）；未完成时保留待验证/待合并状态。
5. 晋升后获取实际 `main`，在保留无关本地工作的前提下更新本地状态；核对最终源码树与已测候选、制品构建输入的一致性，并满足必需检查。合并方式导致提交 SHA 不同可记录映射，但内容变化必须重验并按需重建。确认匹配后才按下节预览、备份和同步正式软件目录；未晋升候选只能进入已授权且隔离的试用/测试环境。

没有 Git 时沿用实际交付方式，不为本规则创建仓库、审查平台或新 CI。默认两分支及按需专项分支、可选 PR 规则替代旧的每任务分支及一律 PR 要求；既有平台保护、必要验证和安装准入仍适用。日常已授权流程不增加例行人工确认，实际目标由项目配置确定。

用 `git ls-remote <remote> refs/heads/<branch>` 或服务端 API 查询实际 SHA，验证预期提交。需核实 CI 时查看目标提交的 CI，而不是其他提交的绿灯。推送错误时检查远端结果后决定是否重试，避免盲目重复。

## 软件目录同步

1. 解析并核对安装目标的绝对路径、实际链接目标、用途和版本；确认操作人已获授权、新制品对应该目标允许的交付源码，且必要审查/检查/发布条件已满足。不要将软件根、磁盘根或用户目录当作临时清理目标。
2. 优先使用项目既有同步脚本预览差异，读取程序文件更新清单与用户数据保留清单；记录替换、删除、新增三类差异及安装前是否存在。备份会被替换/删除的程序文件并核验备份可读/哈希。保留用户配置、排班/业务数据、存档和浏览器数据；涉及迁移时另有已授权迁移与恢复计划。
3. 检查占用进程，按既有授权停机/退出；需用户正在进行的交互或缺少许可时只暂停替换。在暂存目录校验新文件，按清单替换或使用版本目录切换。目录含设置、存档或用户文件时不使用无差别镜像删除。
4. 删除旧程序文件仅依据上一版程序清单与新清单的明确差集，并纳入备份；未知文件保留。不能无限保留确认废弃的 DLL/资源导致混版，也不能扫描后随意删除。
5. 逐文件核对安装后哈希/版本，执行安装目录中的启动与关键新旧功能冒烟，而不是只运行源码开发服务器。检查保留数据状态。
6. 失败时记录受影响环节，恢复已核验的程序备份；仅移除本次新增、安装前不存在且当前仍匹配本次产物哈希的程序文件。新增文件已被其他进程修改时停止覆盖并报告冲突；版本目录方案则切回已验证旧版。按上一版清单验证文件与启动恢复状态，回滚失败明确报告。运行条件缺失时只能报告“文件已同步，运行未验证”。

Windows 路径操作使用同一 shell 的原生 LiteralPath/等价安全参数；跨盘不能假设硬链接可用。脚本执行必须检查返回值，不能以最后一条命令成功掩盖前面的失败。

## 交付记录与中断恢复

每次交付记录：任务 ID、`test` 候选 commit、远端 `main` SHA、采用 PR 或直接合入、产物清单/hash、安装目标用途/版本、备份位置、验证结果和剩余动作。无 Git 时省略提交与合并字段；个人小任务可合为一条结果记录。共同开发另区分 `test` 同步、`main` 晋升及发布状态，记录实际负责人和适用的 PR/审查/CI 证据。结果可保存到项目既有交付记录或本机记录文件。

源文档随源码同步；已明确列入交付范围的帮助文档纳入产物和安装清单，开发日志/决策记录通常只留仓库。纯文档更新按文档规范验收，软件端无内容变化则核对后记录无需更新文件，不凭旧测试结果声称本次重新验证了软件。

事后补充文档会生成另一提交：区分“制品来源提交”与“最终远端文档提交”；如果只改交付记录，可说明源码内容与制品来源一致，不重建相同程序。不把报告文件内容纳入自引用 hash，也不承诺它包含自己的提交 SHA。

远端和安装目录不是原子事务。一个成功另一个失败时分别记录状态，保留已成功环节，恢复后只补失败环节；不得以重复 push、再次覆盖安装或回退远端掩盖部分完成。验证目标状态后有限重试；同一原因持续失败时停止该环节、报告具体原因与所需动作。

## 产物保留与及时清理

交付核验后按 [保留与清理条件](files-and-automation.md) 清除已替代且无需保留的候选包、中间输出和无用试验文件；失败时只清理确认无用的部分，保留复现证据及恢复材料。当前仍在使用或支持的发布版、必要回退副本和用户数据不按普通缓存清理。记录保留版本、实际清理清单及暂缓原因，归档不能替代淘汰。

构建、校验、打包、同步、回退和清理等重复步骤优先串联现有脚本；有收益时编写项目脚本并实际使用，遵循文件规则中的参数、预览、退出码和验证要求。脚本不会扩大原有操作对象或发布权限，不新增后台定时清理。
