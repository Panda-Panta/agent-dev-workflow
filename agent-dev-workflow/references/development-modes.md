# 个人与共同开发模式

首次接管、参与者或交付规则变化时读取本文件，确定模式并补齐必要的工程约定。日常任务沿用项目已有记录；模式只调整协作成本，不改变原有授权、验收或默认多 subagent 并行要求。

## 判定与记录

- **个人模式**：一名负责人统筹实现、集成和交付；主 agent 自行模块化并调度多个有明确边界的 subagent，仍属于个人模式。
- **共同模式**：多人或多个独立 agent/会话各自向同一主线贡献，或需要协调共享工作区、审查及发布。共同模式的协作约定适用于本任务涉及的共享部分。
- 先读现有计划、AGENTS.md、贡献指南和实际仓库约定。公开仓库、存在 remote 或使用 CI 本身不代表共同模式；个人模式也必须满足已有分支保护和审查要求。
- 没有共同维护迹象时按个人模式推进。证据不足且差异会改变写入、合并或发布对象时，只确认该缺口；其余准备继续。模式不能替代用户对操作对象的具体授权。

在现有主计划中记录一次：模式及依据、任务负责人、适用的审查/合并/发布职责、检查入口与交付目标。小项目写一段即可；已有贡献指南或交付配置则链接正文。参与者、目标或规则变化时更新，避免每次重新选择模式。

个人日常更新通常只需现有计划的一段、相关检查和一条结果记录：计划/日志可在同一文件中区分待做与已做，使用说明留 README，知识方法补已有正文；没有新增内容或结构变化就检查并引用，不刷新无意义时间戳。已有记录能覆盖时，不另建计划、日志、复盘或 skill。单独整理非开发操作经验时使用主 skill 的知识分支，不套用本文件的开发协作与发布步骤。

## 两种模式的执行差异

| 环节 | 个人模式 | 共同模式 |
| --- | --- | --- |
| 任务记录 | 当前计划的一段目标、改动、验收和结果；其他想法进已有待办 | 共用任务 ID，写清优先级、负责人、依赖、验收责任和状态，实施前检查是否已被认领 |
| 模块与派工 | 按 [并行派工](parallel.md) 自主拆分、实施，精简记录 | 同一派工规则，另协调既有认领、模块负责人及共享接口 |
| 分支与提交 | 按 [交付规则](delivery.md) 沿用 `main`/`test` 及既定合入方式；每个提交围绕一个完整变更 | 同一分支规则，另协调共享 `test` 的集成批次和候选归属 |
| 文档 | 使用已有计划、README 和任务记录；无实际内容不新建文件 | 按需要补贡献指南、PR 说明、模块负责人；登记入口而不复制规则 |
| 检查 | 按下节执行最低必要检查，复用有效结果；不为小修复搭建新的 CI 平台 | 同一最小检查原则，另满足已有平台必需检查；不因参与者增加重复验证 |
| 审查 | 按影响让独立 agent 核验重要变更；日常小改动不增加例行审查或审批 | 明确维护者及审阅职责；Agent 审查是技术证据，不代替项目要求的维护者审批 |
| 交付 | 沿用已授权目标和方式，一条结果记录即可 | 按实际负责人和目标分别记录同步、晋升与发布状态 |

两种模式的实际并行、单一写入归属、工作区隔离与受限例外均以 [并行派工](parallel.md) 为准；个人模式不免除有效并行，也不制造形式任务。主 agent 只统筹本任务及委派范围，不接管其他贡献者的工作。

## 可复现环境与依赖

首次接管或环境变更时，在 README/已有开发指南中核对：工具链及运行时版本来源、包管理器与锁文件、依赖安装命令、配置示例、启动/测试/构建入口，以及确有需要的外部服务和样例数据。优先引用版本文件和工程脚本，避免多份手抄清单。

配置示例仅放占位值和必要变量名，真实凭据留在既有本机或受控配置中。依赖安装使用项目既定方式及锁文件；不把全局缓存、个人绝对路径或未写出的手工步骤当作所有人都具备的条件，也不为复现要求一律引入容器。

工具链或环境实际变化影响运行时，验证受影响的安装、启动或检查入口；普通更新和新成员接入优先复用仍适用的说明与结果，不默认重建干净环境或重跑全套检查。缺少外部服务时区分离线通过与完整运行未验证。

新增依赖先核对已有能力，记录采用理由、版本约束及许可/分发条件；使用包管理器维护对应锁文件。依赖升级尽量与业务改动拆分；必须联合变更时写清关系和回归范围，不顺手升级全部依赖。工具链或依赖版本变化时同步环境说明。

## 实现取舍与错误处理

把主 skill 的决策原则落实到实际代码，按需要采用，不另建选型表或检查清单：

- 最小正确变更以满足目标、保持受支持行为和实现/维护总成本判断，不以修改行数最少判断。原模型或接口是根因时修正原实现；同一机制反复出错时处理共同原因，避免不断叠加特殊分支、白名单和相互补偿的补丁。
- 在真实外部输入、信任边界及已证实的失败点做必要校验；内部按明确契约协作，不逐层重复空值检查或无目的捕获异常。现有权限、隔离和数据安全边界仍按实际支持场景保留，不能因减少防御代码而删除。
- 失败不得无依据地转成空数据、默认值或成功状态。只在能恢复、转换或交代错误的位置处理异常，保留原因；降级须有明确产品语义，并使调用方能够分辨正常结果、降级与失败，不用静默兜底掩盖根因。
- 先使用满足当前需求的直接实现和已有能力；真实复用或扩展需求成立后再提取稳定抽象。不为假想需求新增框架、插件系统、依赖或通用工具，也不以“未来可能有用”长期维护闲置实现。
- 兼容路径须对应明确支持的调用方、数据格式或平台；临时兼容写清退出条件，确认已废弃且无受支持依赖后清理旧路径。不能擅自缩小支持范围，也不为未知旧版本保留双实现。

## 统一检查与故障反馈

只执行能判断本次目标和受影响行为是否正确的最低必要检查。先选能够发现实际失败的最小检查集，复用工程已有命令，所需检查通过即继续交付；不默认叠加格式、静态检查、测试、构建和端到端全套流程，不为凑检查项新增工具或台账。

同一内容、环境和依赖条件下的有效结果跨模块、角色和阶段复用，不因提交 SHA、分支名或执行人改变而重测。只有相关实现/环境变化、检查失败或新证据暴露具体缺口时，才补做受影响检查；未变部分不重复。日常开发不执行哈希比对，不以例行备份或重复下载、打包证明完成；确有数据恢复需要时采用 [交付规则](delivery.md) 的最小恢复措施。

把 [决策与证据原则](../SKILL.md#决策与证据原则) 落到已有验收记录：目标功能怎样失败 → 哪项检查能发现 → 实际结果、证据类型与缺口。目标要求真实端到端行为时补齐该证据；普通文案或无行为变化的调整采用相称检查，不例行运行整套端到端流程。不得为通过检查删除失败用例、跳过受支持输入或降低既定验收；测试本身确有错误时，依据产品契约与实际行为修正。

已有 CI 调用同一套必要命令；本地已有适用结果时不为仪式再跑一遍，实际平台或依赖差异只补对应检查。平台明确要求候选提交重新执行 CI 时满足该要求，不关闭或绕过，也不自行扩张范围。冲突解决或其他贡献确实改变了相关内容时检查受影响部分；只改变提交身份、没有改变被测内容与条件时复用原结果并说明来源。CI 缺失、失败或等待时如实标明。

真实缺陷先保留复现输入，再为已修复的行为补有价值的回归样例。相同机制反复出错或造成重大影响时，在既有问题/日志中记录原因、缺失的检测及改进动作；需要专有知识才更新领域 skill。不为每次小修复强制写独立复盘报告。

直接阻碍当前目标或验收的问题纳入本次修改；无关风格调整、依赖升级和优化不顺手开展，确有维护价值的发现简记在已有待办。结构优化按 [既定触发条件](planning.md#目录索引与定期整理) 安排，不借当前任务扩大范围。

## 审查证据与影响范围

两种模式的 Finding 都写清适用前提、观察结果或完整静态调用路径、可达后果及证据缺口，影响描述止于证据能够支持的范围。底层可读、文件可构造或某个 helper 未调用，只能证明对应事实；若声称正式业务错误接纳，还需核对入口、校验、调用条件与最终处理路径。链路尚未证实时列为待核实疑点，不当作已证实后果；完整静态路径已经足以证明时，无需为形式补做昂贵或危险实测。

安全类 Finding 先核对当前 Technical Authority：项目现有的权威技术约定、已确认产品契约及架构/安全约束。引用其实际入口与适用版本，结合当前实现确认受支持场景、调用者权限、数据来源及真实信任边界。没有专门同名文件时使用已有可靠约定；关键边界不明就标记待确认，不把文档缺失解释为风险不存在，也不强建新文档、矩阵或审批平台。个人小改动在现有审查记录写必要证据即可。

## 共同开发的审查与贡献入口

开工时确认任务负责人、相关模块维护者、验收人，以及实际合并/发布职责；角色可以由同一人承担，但以项目现有规则为准，不虚构评审人、审批或权限。跨模块接口变化由相关负责人协调后再更新依赖任务。

贡献指南只写项目特有的环境入口、领任务方式、分支/提交约定、检查、审查和发布责任。PR 说明给出问题与最终行为、范围、实际验证、文档及迁移/交付影响；没有相关内容的栏目省略。已有等价模板则复用。GitHub 项目可按需要使用 CONTRIBUTING.md、CODEOWNERS 和分支规则，但本 skill 不自动更改远端设置或发出通知。

作者处理审查意见并给出验证证据；遇到意见冲突，由项目确定的负责人决策。变更完成、待审查、待合并、已合并和已发布分别记录，不能以 agent 自审通过替代剩余状态。对外发消息、请求审阅等动作沿用已有的具体授权和工具规则。

## 同步与发布目标

软件目录按实际用途区分，真实路径与准入条件写在现有交付配置；候选同步、晋升、制品核对与安装程序统一采用 [交付流程](delivery.md)：

| 目标 | 更新条件与证据 |
| --- | --- |
| 个人试用目录 | 已授权的候选版本，完成相关验证并标明来源提交；与共享/稳定目录隔离 |
| 共享测试环境 | 按该环境的验证和协调条件部署 `test` 候选，记录版本及影响；不声称已经正式发布 |
| 稳定/正式目录 | 候选已晋升 `main`，满足必需检查与发布条件，由已授权负责人执行；确认实际 `main`、产物和安装状态一致 |

路径在本机不一定表示个人试用目录，应以实际用途判断。单人项目可以只有一个已授权正式运行目录，不要求拆出所有环境；满足交付条件后直接更新该目录。无 Git 的任务沿用实际交付方式，不为流程新建仓库。

`test` 已推送但审查/晋升未完成时，保留“开发完成、test 已同步、待合并/待发布”的状态；已授权的独立试用可以继续，正式目录不得被此候选自动覆盖。到达真实外部等待点时留下接续条件，不为凑齐同步而改写状态或绕过规则。

数据格式/数据库有迁移时同时考虑仍在使用的旧版本；回退程序不等于恢复数据，恢复方式必须能覆盖实际迁移。
