# 并行派工与集成

## 调度方式

先沿用项目的 [个人/共同模式](development-modes.md)。以下主 agent 的统一管理限于本任务及其委派范围；共同开发先协调已有贡献者、任务认领与模块负责人，不把他人的分支、文件或发布职责默认为自己所有。

1. 主 agent 自行把目标和验收映射为职责明确的模块或工作包，写清输入输出、依赖、唯一写入归属及检查；无需用户另行安排分工。沿用现有架构，工作包不必对应新增目录或代码模块。
2. 从这些工作包提取依赖图；确定共用接口、模型、样例或必要骨架后，按真实依赖分批。具备独立实施条件时，默认将各模块分给至少 2 个 subagent 同批并行开发，不等用户再次要求开启并行。
3. 使用当前会话提供的 subagent 工具，避免创建用户侧新聊天代替内部协作。普通子任务继承可用模型配置，不擅改全局模型和并发配置；在实际槽位和资源范围内安排批次，不为耗尽槽位派工。
4. 有 Git 时默认在 `test` 的共享目录协作，同一文件只有一个写入负责人。确需工作区隔离且工具支持时，可从固定 `test` 提交创建 detached HEAD worktree；按需专项分支遵循 [交付规则](delivery.md)，不按 agent 数量例行建分支，也不强制同一分支多次检出。明确真实 cwd 与基线；隔离不会复制未提交文件，也不隔离所有外部资源，构建输出、测试数据和必要端口仍需区分。无 Git 时按目录和文件归属协作。
5. 主 agent 管理共享接口、入口装配、集成队列和整体验证，不重复实现已委派工作。按依赖顺序检查和合入，只对失败、范围变化或新证据追加检查。

在现有计划或任务记录中保留模块/任务与 agent 的对应关系、并行批次、实际执行和结果；仅有真实重叠执行才能称为并行。事后安排两个审查者核验主 agent 已完成的实现，不算多个 subagent 并行开发模块。

源码共享时，入口、公共 schema、依赖清单、锁文件、代码生成结果和迁移序列由一个负责人统一修改。子 agent 如需越界先报依赖，主 agent 重新分配；不能覆盖别人的改动后才通知。

共享 `test` 的 Git 索引、提交、分支切换和远端同步由主 agent 串行执行，子 agent 只修改授权文件并回报结果，不在其他任务写入期间切换 checkout。隔离 worktree 的成果由主 agent 核对差异后按批集成回 `test`，再做集成验证。共同开发先协调其他贡献者正在使用的 `test`；候选选择及晋升 `main` 的条件按 [交付流程](delivery.md) 执行。

产物与辅助脚本也遵循单一写入归属：按 [文件管理规则](files-and-automation.md) 为各任务划定中间结果、报告和试验脚本的目录；共同的构建/清理脚本由一个负责人维护。复用同一脚本时传入独立输出位置，不能让一个任务清空另一个任务的 build 或临时区。共享发布产物和备份由对应负责人统一保留/清理。

派工时也分配受影响的使用文档；本任务的开发日志、更新日志和文档素材由主 agent 汇总，跨贡献者共享文件按项目明确的单一写入/合并归属处理。子 agent 回报已验证操作和日志素材，避免多人同时写共享记录。

主 agent 在派工前检查任务共用入口与约束，随工作包提供现有工具/工程命令、文档/样例/领域 skill 的真实入口、适用版本与已知限制，明确哪些已检查、哪些模块特有资源仍待补查。子 agent 在本模块实施前完成定向补查并优先复用，不重复全库盘点或各自重写同一工具；部分检查不能标为全部完成，共用能力的缺口先报告并确定单一维护者。工具代码、详细说明与运行输出各归其位，输出路径仍需独立；共享的是入口，不是可被并发覆盖的状态。

影响并行安全的共用工具副作用、公共接口、写入归属与输出隔离，由主 agent 在相关实施派工前核实；未明确时可先分配只读调查，并推进不依赖该缺口的工作。模块特有资源列为子任务前置检查，完成前不执行依赖它的修改或命令。

## 可复制的派工约定

```text
目标 / 模块或任务 ID / 并行批次：
工作目录 / 固定基线版本（有 Git 时） / 共享 test、detached HEAD 或已规划专项分支：
模式 / 负责 agent / 任务认领 / 协作对象及依赖任务（适用时）：
必须读取的计划段落、模块规则和领域 skill：
已检查的可复用工具/命令、文档/样例入口及适用性、已知缺口；本模块需补查项：
用户目标 / 受支持场景与需保持的旧行为 / 已知问题及根因证据（未知项标明）：
允许修改的文件 / 唯一写入归属：
本任务产物、报告、临时脚本位置 / 可清理范围及保留条件：
输入输出 / 公开接口、样例、错误与兼容约定：
可并行部分 / 必须等待的前置条件：
验收和必要检查 / 能发现的目标失败 / 证据覆盖及未验证项：
限制：只做本任务，不自行递归派工、新建分支、操作 Git 索引/提交/切换、推送或安装。
交付：修改路径、行为说明、实际命令与结果及证据类型、未验证项、接口变更、风险。
附本任务新增/复用脚本入口、最终产物位置、已清理内容及仍需保留的临时材料。
```

给子 agent 足够完成任务的原始信息；独立审查者需要需求、差异和可运行环境，不把“实现已经正确”的结论当作前提。

派工和审查沿用 [决策与证据原则](../SKILL.md#决策与证据原则)。只提供本任务需要的验收与证据要求，不给每个子任务强加完整端到端流程。子 agent 说明证据类型、能发现的目标失败及缺口；主 agent 负责补齐集成层验证，不能把各模块的局部通过相加当成整条业务链已验证。

审查派工按需附当前 Technical Authority 的入口、版本和已知边界；Finding 的回报与核对标准统一采用 [审查证据与影响范围](development-modes.md#审查证据与影响范围)，不重复建立另一套审查要求。

## 小任务与受限环境

个人模式和低风险只影响文档、检查与协作成本，不是免除多 subagent 的理由。没有两个独立实现单元时，先寻找真实有价值且能独立开展的测试、文档或分析工作包，与实现合理并行；不要让两个人同时改同一个小函数，也不要为凑数量增加无关文件或架构。准备、实现与审查分别记实，审查者不能在尚未完成的代码上给最终通过结论。

用户当前明确禁用子 agent、工具不可用或槽位/资源受限、实际前置依赖未满足，或确实没有独立工作时，只对受限部分等待或串行处理。记录具体原因、受影响任务及后续安排，保留其他可行的并行工作；不能用笼统的“小任务”跳过拆分判断，也不能把依次执行写成并行。

## 集成完成条件

- 主 agent 读过实际 diff 与相关上下文，确认没有写入越界、无关修改或用户数据。
- 模块/任务的 agent、批次和实际结果已记录；受限部分有具体依据，未将审查或串行执行冒充模块并行开发。
- 共享契约与调用方一致，新功能和受影响旧行为在集成状态下按目标验证；记录证据的实际覆盖，未验证目标不标完成。
- 按影响对重要变更安排独立 agent 审查，日常小改动不增加例行审查或审批；问题修复后只重验受影响部分。
- Finding 的前提、路径与影响有对应证据；安全结论已按当前技术权威约定核对真实边界，未证实疑点与已证实问题分开记录。
- 根计划、模块索引、相关领域 skill 和交付清单与最终实现一致。
- 本任务的集成结果与交付记录交由主 agent 汇总；subagent 不自行发布，后续晋升和安装按 [交付流程](delivery.md) 由已授权负责人串行执行。
