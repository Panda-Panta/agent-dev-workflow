# 规划与源码结构维护

## 首次接入

先读仓库真实布局、工程命令、现有架构文档和 AGENTS.md，再决定需要补什么。源码根与 Git 根可能不同，单体仓库有多个软件时，根索引链接各软件计划。

按 [开发模式](development-modes.md) 在现有计划记录个人/共同模式及依据，关联真实环境、检查和交付入口；共同模式再明确任务认领、审查/合并/发布责任。个人小任务复用已有段落，不为采用本流程新增贡献平台或例行审批。

按需文档落点（不是必建清单）：

| 位置 | 唯一职责 |
| --- | --- |
| `DEVELOPMENT_PLAN.md` | 产品目标、功能清单、架构、模块接口、里程碑、当前增量计划或链接 |
| `PROJECT_STRUCTURE.md` 或根计划/README 的等价索引 | 真实文件树、模块职责、依赖方向、常用入口 |
| `AGENTS.md` | 执行规则和上述文档/领域 skill 的触发入口 |
| `README.md` / `DEVELOPMENT_LOG.md` | 用户入口与开发事实记录；可以复用现有等价文档 |
| `docs/changes/` | 较大更新的增量计划与验收记录，按需建立 |
| `docs/delivery.md` | 已确认的远程、安装目标、产物清单、备份和验证方式 |
| `.agents/skills/` | 随源码维护的软件专有领域 skill |

已有等价文件则登记映射并复用；根目录可保留短索引指向正文。合并到现有 AGENTS.md，保留其他规则。不要以模板覆盖已有计划，也不要为填齐目录制造空文档。

首次确需建立完整计划时，可按需采用 [完整计划模板](../assets/DEVELOPMENT_PLAN.template.md)；已有计划只补缺口，不要求填齐全部表格。

首次接入或更新涉及使用方式时，按 [文档与开发记录规范](documentation.md) 明确需要维护的使用说明、版本更新说明和记录落点；日志、决策和交接复用现有事实来源。

## 文件分类与生成位置

按 [资源检查与文件管理规则](files-and-automation.md) 完成任务前的工具、文档和领域 skill 检查。在现有任务段简记“资源路径/命令 → 用途 → 适用性与复用决定/缺口”，小改动一行即可；续作只复核受影响或已变化部分。

在现有结构索引或开发指南维护简短的文件分类映射：类别、真实路径、生成命令/负责人、保留与清理条件。计划只链接该映射；本次出现新类别或路径时更新。工具、文档和运行输出分开，具体目录与清理规范以文件管理规则为准，不在计划维护第二套正文。小项目只创建实际需要的目录；并行任务的输出归属按 [派工规则](parallel.md) 确定。

## 完整计划应足够回答的问题

1. 为谁解决什么问题；受支持场景、现有产品行为、输入输出和非目标是什么。问题与根因有哪些证据；尚未确证的原因标为假设并给出核验动作，新需求不编造故障根因。
2. 功能有哪些：稳定 ID、优先级、状态、验收、所属模块。已实现功能与计划功能区分。
3. 代码如何组织：模块边界、公开接口、允许的依赖方向、数据流/控制流、入口与装配。
4. 哪些数据需要持久化；错误、并发、恢复、权限、性能等本项目相关约束如何处理。
5. 可复用哪些已有工具、命令、文档、样例或领域 skill；适用性、缺口与改进/新增理由是什么。为什么所选方案是满足目标的最小正确变更；新增复杂度的实际需求或已证实失败依据、收益与维护成本是什么。依赖哪些库或平台，哪些约束已从当前环境确认。
6. 如何按 [并行规则](parallel.md) 自主模块化并派工：模块/工作包与验收对应关系、接口、依赖、实际 agent 归属、批次和集成负责人；受限部分及原因是什么。
7. 如何证明可用：新功能验收、旧功能回归、必要的构建和实际运行检查。所选检查能否发现目标功能的真实失败，分别覆盖什么行为、还有哪些证据缺口；模拟或指标结果不替代未验证的真实行为。
8. 如何按 [交付规则](delivery.md) 交付：已有远端和软件目录、候选及实际主线、PR 或直接合入方式、更新清单、保留数据和回退；确需特殊分支时在本计划补用途、负责人、基线、合入目标与结束条件。

未涉及项明确不适用；影响实现的未知必须给出调查或确认动作，不能以猜测填满模板。设计冻结的是当前实现批次的接口，不阻止有依据地修改计划；变更契约时同步通知依赖任务。

方案按主入口的 [决策与证据原则](../SKILL.md#决策与证据原则) 取舍，依据和成本收益写入已有决策段；普通小改动不另建选型表。普通可逆选择由 agent 根据现有工程作决定；关键缺口与超范围操作许可分别按 [协作规则](human-first.md) 处理，继续不依赖该缺口的工作。已有明确要求、决定或授权沿用，不重复审批。用户修正约束后更新当前计划和依赖任务。

## 增量计划与兼容性

为每次更新标出“新行为、保持的旧行为、允许改变的旧行为”。检查实际受影响的调用者、数据读写者和配置，而不是只看变动文件数。

- 新特性拥有清楚的模块入口、配置归属和测试。共享能力通过已有抽象复用。
- 接口或数据需要变化时，选择明确的版本化、兼容适配或可验证迁移；保存旧样本做读写验证。
- 特性开关只在灰度或回退确有用途时使用，写明默认值及删除条件。
- “不影响旧功能”以保持约定行为和回归证据表达；测试不能证明所有未来场景绝无缺陷。

小修改在主计划写一段目标、修改点、分工/批次、验收和交付即可，无需固定大表；实际受限时注明具体原因。较大更新使用 [增量计划模板](../assets/change-plan.template.md)。核心架构决定改变时同时改主计划，而不是只留在聊天里。

计划或任务记录保留本次已知的流程文档/领域 skill 入口；发现新方法时先记实际证据，收尾按 [知识沉淀规则](domain-skills.md) 更新唯一正文。没有新知识时检查即可，不预先创建空 skill、教程或复盘。

任务 ID 在计划、问题记录、提交/PR 和日志中保持可追踪，已有记录则链接复用。优先级和状态按实际需求维护，共同开发区分开发完成、待审查/合并与已发布。依赖升级、技术债及故障反馈按 [工程约定](development-modes.md) 记录，不把无关待办塞进当前变更。

## 目录索引与定期整理

先复用现有结构索引。首次缺失时，在源码根已有计划或 README 补入实际目录、模块职责和入口；结构复杂才使用 [结构模板](../assets/PROJECT_STRUCTURE.template.md) 拆出独立文件，并保留根入口。这样持续满足结构可查看、可更新的要求，小任务无需只为文件名另建文档。

确认 Python 可用后，从 skill 的真实绝对路径调用工具；路径只作占位，使用当前项目的实际值：

```text
python "<skill>/scripts/update_project_structure.py" --root "<source-root>"
python "<skill>/scripts/update_project_structure.py" --root "<source-root>" --check
```

查看 `--help` 获取输出位置、深度与排除参数；索引复用已有文档时用 `--output` 指向该实际 Markdown。把项目实际参数记录在结构文件人工区，并在后续/CI 检查中使用同一组参数；不要写死当前机器的 skill 绝对路径进共享 CI。

工具仅更新 UTF-8 Markdown 中标记内的目录树，人工补充模块用途、重要入口和边界。Git 模式使用受跟踪与未忽略文件；检测到链接时，为避免 Git for Windows 跟随 junction，明确降级到不遍历链接的文件系统模式，此时不应用 gitignore。Git 不可用时也会说明降级。预检查只读目录元数据，可能检查展示规则已排除的目录；超大仓库优先复用成熟的项目索引工具。保留裁剪深度和排除规则，避免把摘要当完整清单。

每次交付核对目录树及本次涉及模块的职责、依赖和文档链接，有变化才更新。默认每个里程碑或累计 5 次交付对全项目检查一次职责漂移、循环依赖、无调用模块与废弃入口；项目可在现有计划调整周期，并记录上次审查和结论。需要整理时独立成任务，先查引用、构建配置和打包路径；删除依据必须是确认废弃，不能仅凭文件名陌生。

以上周期用于全项目审查，不推迟本任务过期文件的及时清理。搬迁/移除文档和脚本后同步调用命令、导入、文档链接、生成/打包配置及索引，并验证受影响入口；不能只更新目录树而留下失效调用。
