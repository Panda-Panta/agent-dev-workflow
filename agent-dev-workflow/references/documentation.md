# 文档与开发记录规范

## 开工先查已有资源

方案定稿、派工和实现前，按 [资源检查规则](files-and-automation.md) 从根导航定向查阅相关指南、接口/参数规范、历史决定、已知问题、样例及领域 skill，并定位其引用的现有工具。核对文档适用版本和当前源码/配置；过期说明、失效链接及未经验证的样例须核实，不能把“已有文档”当作复用依据或测试通过。现有内容够用就引用，缺口只补到唯一正文；主 agent 将适用入口与已知限制带入派工，子 agent 按模块补查。

## 文档分工与最小集合

先使用现有等价文件，在源码根 README 或主计划登记唯一入口。保留根目录导航和已有规划/结构入口，下表文件按内容需要拆出；不为满足名称建齐一套文件。小项目的使用说明可写进 README，开发记录可直接复用带日期和任务 ID 的增量计划。已有任务系统或文档站能提供同等记录时链接它，不再维护第二份正文。

| 类型与建议位置 | 读者与职责 | 更新时机 |
| --- | --- | --- |
| `README.md` | 用户和维护者的入口：软件用途、支持范围、快速上手、文档导航 | 安装、启动、入口或支持范围变化 |
| `docs/USER_GUIDE.md` | 使用者：按真实任务说明操作、输入输出、配置和排错 | 功能、界面、参数、默认值、数据位置或升级流程变化 |
| `DEVELOPMENT_LOG.md` | 开发者/接手 agent：本次做过的事、验证、问题和接续动作 | 每项开发任务开始、重要检查点、交付或中断 |
| `CHANGELOG.md` | 升级用户：新增、修复、兼容变化、已知问题和必要操作 | 用户可感知变更进入候选版本；发布后补实际版本和日期 |
| `docs/decisions/` | 后续维护者：难以从源码看出的重要设计取舍 | 架构、公共契约、存储、重大依赖等长期决定发生变化 |
| 当前计划的“交接/未完成”段 | 下一位执行者：现在在哪里、下一步怎么继续 | 工作中断、换 agent/会话、仍有阻塞或未验证项 |

每项开发更新至少留下简短事实记录。对未受影响的用户文档注明“检查无变化”即可；不新建空文件，不按字数考核，不把同一事实复制到计划、日志、交付报告各一遍。计划写待做与验收，日志写已发生的事实；详细验证和交付清单用链接复用。

任务完成前，按 [领域知识与任务流程沉淀](domain-skills.md) 对照已有正文检查新知识。尚未记录的有用流程或纠错应补进现有领域 skill/文档；普通小任务几行足够，已有记录适用则简记检查结果。知识正文写“下次怎么做”，本次日志只记新增/修订的要点、路径和证据；未完成内容留草稿与交接，不标为已验证流程。

按 [文件管理规则](files-and-automation.md) 在根目录保留主入口，较长指南、增量计划、决策和历史记录归入现有 `docs/` 分类；skill 的参考说明沿用 `references/`。长期工具代码放 `scripts/`、`tools/` 等专用目录，详细说明与工具入口互相链接，不把独立可执行脚本、构建包和原始诊断产物放进文档目录。简短帮助、docstring、工具局部 README 及文档内的示例片段可就近保留，完整正文只维护一处。一次性任务也分开脚本、记录/说明和输出；现有混放按本次范围核对引用后逐步整理，勿为统一名称搬迁整套文档。

## 开发日志

采用 [开发日志模板](../assets/DEVELOPMENT_LOG.template.md)。每项任务包含：

- **定位**：日期/时区、任务 ID、目标、关联计划/问题和基线版本；资源检查的复用入口、约束或缺口可在此简记，计划已记录则链接。
- **实施**：最终修改、涉及模块、关键决定及理由、影响的旧行为；复现得到的失败原因和修复依据。
- **证据**：实际检查命令/操作、工作目录、必要的执行环境/权限、退出码或可观察结果、对应版本/目标和日志/样例位置；区分通过、失败、未运行，分别标明源码、候选、安装和运行阶段的证据范围。
- **交付**：来源提交/制品、远端和软件目录的各自状态，链接权威交付记录。
- **接续**：剩余问题、已知限制和下一步；阻塞项写清所需信息或外部条件。

开始时只写目标/基线/进行中状态，随有意义的操作补记事实；临时命令、手工补做或沙箱外执行同样纳入记录，结束前汇总最终状态。重试成功另记修正及验证，不覆盖首次失败；用户纠正或撤销时注明被替代的结论与当前有效状态。记录可审查的事实与理由，不复制整段聊天、逐条工具调用或推测性流水账。

面向用户的简短汇报按 [协作规则](human-first.md) 组织，详细证据留在本记录并提供入口。聊天简洁不减少计划、操作说明和验收所需内容；工作假设标明待核验，用户纠正影响范围或接口时同步修订相关计划和验收。

多 agent 各自在回报中提供记录素材，本任务的共享日志由主 agent 汇总写入；共同项目遵循既定文档归属/合并流程，不接管其他贡献者的记录。独立工作区的临时记录按需汇总，不把并行写入冲突转移到文档。

运行时诊断日志与开发日志分开：大体积原始日志、转储和截图放受控产物位置，开发日志只给必要摘要、任务关联和可访问的证据入口。提交前去除令牌、真实用户数据和机器私有信息；源码引用用仓库相对路径，本机交付路径留在既有本机记录中。日志过长按年份/月归档，保留根索引和未完成事项，更新引用后再迁移。

记录档案保留可追溯事实，过期临时输出按保留条件实际清除，不把全部垃圾改名归档。清理被文档引用的原始材料前，保留必要证据或更新索引，明确材料已按策略清理及仍可用的摘要；未解决问题的唯一证据继续保留。已废弃且无独立历史价值的重复文档经引用核对后删除；重要旧决策保留替代关系。

执行中确认的启动方式、工作目录、环境限制和日志位置等可复用前提，及时补进现有开发/运行指南，并从根 README 或主题目录链接；任务日志保留本次适用版本、对照和证据。需要比较的日志在自动轮转前保留到本任务证据目录，使接手者能按“任务 → 操作说明 → 工具 → 证据”找到对应内容。

## README 与使用文档

README 可用 [入口模板](../assets/README.template.md)；完整操作说明可用 [使用手册模板](../assets/USER_GUIDE.template.md)。按用户目标组织，不把代码模块列表当使用说明：

1. 软件做什么、适用版本/平台、需要哪些前置条件；已验证支持与计划支持分开。
2. 安装、启动和首次配置；示例标明 shell、工作目录与占位参数。
3. 一条从启动到获得可观察结果的最小成功路径，给出输入样例、操作与预期输出。
4. 主要功能的入口、步骤、关键选项/默认值/单位、取消或失败时的结果，说明实际保存位置。
5. 用户配置/数据的保存、备份、升级、迁移与恢复；卸载说明区分程序文件和用户数据。
6. 常见问题按“症状 → 检查方法 → 处理 → 何时提供何种诊断”编写，保留已知限制。

内容以实际实现、已验证产物及现有配置定义为依据。避免重复抄写可自动生成的 API/参数清单；优先链接已有规范。开发环境、测试和贡献说明按需放单独开发者章节或现有 CONTRIBUTING 文档，普通使用路径保持简洁。

开发环境说明与贡献指南按 [开发模式](development-modes.md) 维护：个人项目保留最小环境/检查入口；共同项目按需要记录接入、任务、审查和发布约定。已有文档足够则复用，不因切换模式复制整套规则。

功能实现与相应使用说明在同一更新中完成。新增/变动的关键操作按风险验证，记录目标版本、环境和结果；已有实际执行证据能覆盖当前说明时直接引用，不为补文档重跑危险、昂贵或有副作用的操作。首次安装/配置的验证使用干净或明确说明的环境，避免依赖未写出的个人配置；缺少实际运行证据就标明未验证。截图需来自对应实现，凭据和个人信息脱敏；截图只在确有帮助时增加。

源分支文档可描述候选功能，但标明“未发布/适用候选版本”；面向已发布用户的入口和随安装包提供的说明对应实际发布版。文档更新不等于软件已经发布或安装。

## 更新日志、决策与交接

**CHANGELOG** 沿用项目版本策略。未发布变化先进入 `Unreleased/未发布`，按新增、修复、兼容变化、已知问题等相关类别写用户影响；没有内容的类别省略。发布验证后填写实际版本/日期和必要的迁移操作，不为写文档擅自发布、打标签或虚构版本。内部重排文件但使用无变化，可以仅记开发日志。

**重要决策** 至少保留问题背景、选定方案、关键理由、取舍/兼容影响、证据及状态。简单决定记现有计划/日志；需要长期独立引用才新建带稳定编号的 ADR。后续推翻时将旧决定标为被替代并链接新决定，让维护者看清原因。

**交接** 写清实际分支/提交或未提交文件、已完成与未验证项、正在运行的任务/服务、阻塞条件、下一项具体动作及相关日志/领域 skill。接手者先检查真实工作区和外部任务状态，不能仅凭旧记录判定测试、推送或安装仍然成功。完成任务可在日志收尾，不额外生成一份重复的交接文件。

## 文档验收与交付

每次完成前检查受影响的文档：入口可找到，链接和源码路径有效，命令/参数与实现匹配，样例与预期结果明确，版本/发布状态准确，未验证项可见，敏感信息已处理。复用项目现有 Markdown/链接检查；不为一段文案建立新测试框架。

重复的文档生成、链接核验、产物索引或交付清单整理，优先调用已核对适用性的现有脚本；确认缺口且有复用价值时补入项目工具目录，说明放文档目录。新增或行为变更的脚本按风险执行验证，单纯文案修订不强制重跑未变脚本。脚本输出写到约定目录，仅更新声明的生成区域，人工维护的说明继续保留。

文档与相关源码一起提交和同步。软件分发包含帮助文档时，把变动文档纳入产物/安装清单并核验；只供开发使用的日志和 ADR 留在仓库，不自动塞进软件目录。纯文档改动执行相称的文档检查，不把先前软件测试结果记成本次重跑；软件端无内容变化时记录已核对、无需更新文件。
