# Agent 软件开发通用流程

主 agent 负责需求拆分、计划、协调、集成和交付；subagent 负责边界明确的工作包。以本文件的原则和阶段为入口，遇到相应操作再读取链接的细则。规则在对应 references 维护，模板只记录项目事实，避免多份规程分叉。

## 入口与任务边界

- 开发前读取项目 AGENTS.md、现有计划、结构索引和相关领域 skill；确认源码根、分支、用户未提交/已暂存修改、未完成工作及交付目标。用户当前具体要求优先，沿用已明确的决定和授权，不新增例行审批。
- 方案定稿和派工前，按 [资源与文件规则](references/files-and-automation.md) 定向检查可复用的工程命令、工具、文档、样例和领域 skill；核实适用性，在现有记录简记入口、复用决定及缺口。工具实现与详细文档分别存放并互相链接。
- 首次接管或协作关系变化时按 [开发模式](references/development-modes.md) 确定个人/共同模式，后续沿用。个人小任务复用现有计划的一段和结果记录；共同模式补认领、共享资源及审查/合并/发布职责。均不为流程强建仓库、CI、PR 或多套文档。
- 已委派的 subagent 仅执行获派范围、相关约束和验证，不重启完整流程、不自动递归派工、不自行推送或安装。用户“仅计划/先分析/暂不推送/不使用子 agent”等限制优先，未执行步骤如实记录。
- 纯问答与只读审查不启动开发或同步；只读审查适用下列原则及审查细则。仅沉淀非开发操作经验时，检查已有资源后执行第 7 节，不新建开发计划或派工，不因记录而推送、安装或干预运行中的会话。

## 决策与证据原则

- **目标优先、复杂度相称。** 技术决策以用户真实目标、支持场景和现有产品行为为准。先确认待解决的问题及其根因，再选择满足目标的最小正确变更。新增防御、抽象、依赖或更换技术方案，应有实际需求或已证实的失败场景支持，其收益须足以抵偿实现与维护成本。存在实质性取舍时，比较保留现有设计的可行方案；改变产品行为、架构边界或授权范围时，由相应决策者确认。尚未确认的根因写明假设及核验办法，不以猜测代替证据。
- **真实行为优先。** 以用户目标和现有受支持行为判断完成情况。测试、模拟环境和指标只证明其实际覆盖的内容；验证方式必须能够发现目标功能的真实失败。模拟测试不能冒充真实端到端验证，指标改善不能以破坏目标功能为代价。真实行为尚未验证时，明确证据缺口，不宣称目标完成；可分别报告已实现、已检查与尚未验证的部分。
- **后果与证据匹配。** 每条 Finding 声称的影响不得超出实际观察或完整静态调用路径能够证明的范围。底层接口可读取、文件可构造、某个 helper 未被调用，均不自动证明正式业务结果被错误接纳。安全类 Finding 应先按当前 Technical Authority 核对真实信任边界与适用场景；具体证据与权威来源的核对按 [工程验证与审查约定](references/development-modes.md) 执行。

相应决策者已明确的需求、决定和授权可作为确认，沿用其覆盖范围；超出既定范围的实质变更才补充确认，普通可逆实现选择不新增审批。验证按任务真实目标和影响选择；文档任务不因此要求业务端到端运行。只读审查使用这些原则及相关证据约定，不启动开发、模块派工、推送或安装。

## 执行与沟通

按 [协作与自主执行](references/human-first.md) 处理缺失输入、授权、用户纠正、分歧和汇报：普通可逆选择自主决定，关键缺口尽早澄清并继续独立工作；逐段验证后持续完成已授权目标，相关失败修复后复测。汇报先说结果或实际状态，再给必要证据；计划和首个片段完成只是进展。

## 1. 形成可执行计划

按 [规划与维护](references/planning.md) 维护一份从源码根可达的完整计划。新项目/首次接管/架构变化补齐功能清单、代码与目录结构、模块职责、接口依赖、验收、兼容、交付与维护安排；已有权威正文继续使用。普通更新补当前任务段，较大更新可用 [增量模板](assets/change-plan.template.md)，不另建重复总计划。

主 agent 自主将目标拆成工作包，确定输入输出、共享接口、依赖顺序、独占写入归属、验证与实际输出位置。沿用既有架构，不为并行制造无用模块；新文件先按资源与文件规则分类。共同模式再核对相关维护者及共享状态。

开工前应能从现有记录找到：目标/非目标与验收、根因或待验证假设、相关资源及缺口、影响模块与旧行为约束、写入归属和依赖、检查方式及交付目标。小任务几行即可，模板字段按需要采用。

## 2. 模块化并行实施

按 [并行派工](references/parallel.md)，独立工作包默认交至少两个 subagent 同批实施，依赖任务分批；派工传递资源、输入输出契约、独占文件、验收及回报要求。共享接口、锁文件和 Git 操作由单一负责人协调。

个人模式也先检查真实可拆工作。确无独立工作、用户限制或工具/依赖阻碍时，记录具体原因，仅简化受限部分；不凑任务、不争写，不以事后审查冒充并行。主 agent 处理未委派工作并检查实际产出，统一集成和交付。

## 3. 实现与自动化

新能力放入职责明确的模块，通过现有接口或装配入口接入；为新行为和受影响旧行为明确验收，共享模型、存储格式、公开 API 变化写明兼容、迁移与回退。缺陷先尝试复现；间歇故障保留现场、缩小条件并核验假设，说明复现限制。

按决策原则选最小正确变更，避免无需求的抽象、插件系统或大规模搬迁。行为变化补有价值的验证；无行为变化的小调整采用相称检查，不写仅复述实现的测试。

优先复用工程命令；重复、多文件或易错步骤有实际收益时，按 [自动化规则](references/files-and-automation.md) 编写并使用脚本，明确输入输出、重跑/覆盖、失败处理和验证。长期工具、一次性试验及其产物分开存放，保留有用的命令、版本、初次失败和修正证据。

## 4. 集成、验证与审查

主 agent 核对实际差异、依赖与子任务证据后集成，按 [工程验证与审查](references/development-modes.md) 选择能暴露目标功能失败的检查，执行新行为验收、受影响旧行为回归及项目必需检查；公共契约、持久化或核心算法变化扩大相关回归。重要变更由未编写该部分的 agent 审查，仍满足项目必需的维护者审批。

证据绑定实际候选、环境与命令。记录结果、覆盖和缺口；构建、模拟、源码运行、安装文件与真实运行各自只证明对应环节。相关失败修复后重验，未验证或受阻如实保留，不将有问题的产物投入使用。

## 5. 维护结构、文档与文件

每次更新核对源码根可达的结构索引，结构/职责/入口变化才更新。按 [规划规则与目录工具](references/planning.md) 优先复用既有索引与工具；里程碑或累计 5 次交付审查全项目结构，项目可调整周期。日常只处理本次影响，较大搬迁另列重构并验证。

按 [文档规范](references/documentation.md) 更新本次事实日志、受影响使用说明、必要版本说明及交接；个人记录可合并但区分计划与已做事实，重复信息用链接。相关领域规则在同一更新中维护，新流程的记录方式见第 7 节。

按 [分类与清理规则](references/files-and-automation.md) 分开工具、详细文档、构建中间产物、验证报告、最终产物和备份；生成、替代、试验结束及交付时及时清理已确认过期内容。清理先核归属、引用、保留条件和真实路径，保护用户/他人文件、在用版本、必要回退和未结问题证据。

## 6. 同步远端与软件目录

处理 Git、打包或安装前读取 [交付与同步](references/delivery.md)，由已授权负责人串行协调。默认 `main` / `test`：在 `test` 开发、集成、验证，通过后按既定偏好 PR 或平台允许的直接合入并普通推送 `main`，满足实际保护与必需检查。特殊需要可建按用途命名的分支并简记生命周期；普通任务/每个 subagent 不自动建分支，不擅改已有分支。无 Git 时沿用实际交付方式。

固定已验收候选；候选或 `main` 变化先在 `test` 整合并重验，不夹带他人未验收工作。按清单生成制品，核对实际 `main` 与制品来源后再同步正式软件目录；未晋升候选只进已授权且隔离的试用/测试环境。

按差异清单预览、备份和同步程序文件，保护用户配置、存档与数据；分别核对远端提交、安装文件和目标环境运行，失败按已验证备份恢复。目标缺失只暂停依赖该目标的环节，其余授权工作继续；本 skill 不自动授权新远端、公开发布、强推或删除用户数据。

## 7. 沉淀新流程与交接

按 [领域 skill 与流程知识](references/domain-skills.md) 检查本次尚未记录的有用经验和失效方法：简单方法补现有文档，复杂、稳定且易错的流程更新或创建领域 skill；已有正文足够只引用。记录适用范围、工具入口/参数、环境准备、预检与正式步骤、产物判据、失败恢复及证据边界，字段按实际需要采用。

主 agent 汇总子任务发现与交付阶段新事实，知识正文说明下次怎么做，日志记录本次发生什么并链接。复用已有证据，不为写记录重跑昂贵或有副作用的操作；未完成/未验证步骤留草稿与接续条件，不写成成功流程。补充文档按实际维护位置同步，程序内容未变无需重建。

## 完成判定

核对以下状态后汇报功能结果、证据和未完成项；这是状态检查，不是每次必填表格，个人小任务可合成一条结果记录：

| 项目 | 核对内容 |
| --- | --- |
| 实现与并行 | 工作包、实际归属/结果、受限部分的具体简化原因 |
| 验证与审查 | 完成/失败/未验证，证据覆盖及缺口 |
| 计划、结构、文档、工具 | 已更新/检查无变化，相关入口、脚本结果及整理清理情况 |
| 新流程知识 | 已补并链接/现有记录足够/无新增；未完成交接 |
| 远程仓库 | `test` 与 `main` 实际状态、提交及 PR/直接方式；专项分支状态（如有）或不适用 |
| 软件目录 | 目标用途、版本路径、文件与运行分别验证/待发布/受阻/不适用 |

有阻塞或证据缺口就保留对应状态，不宣称“全部完成”或“绝不影响旧功能”。
